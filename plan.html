개요

Dudung은 PC 화면공유와 모바일 카메라로 송출하고 비로그인으로도 시청하는 라이브 방송 서비스다. 마감은 2026-11-19 23:59다. 평가 항목에 없는 것(k8s 등)은 범위에서 뺐고, 월 0원으로 운영한다.

영역결정
앱Next.js 단일 앱, stateless. 쓰기 작업은 REST Route Handler, 실시간 알림은 SSE
인증jose로 JWT 직접 구현, access + refresh rotation(30초 유예), httpOnly 쿠키
미디어MediaMTX 직접 운영(WebRTC). 송출은 WHIP, 시청은 WHEP. TURN 없이 TCP 폴백(ICE-TCP)
녹화MediaMTX가 서버에서 녹화(fMP4) → 워커가 MP4 하나로 합침 → Cloudflare R2
데이터PostgreSQL + Drizzle, Redis (토큰·락·rate limit·큐·pub/sub)
배포Oracle Cloud Always Free ARM 서버 1대(1 OCPU / 8GB, 오사카), Docker Compose + Caddy, DuckDNS 도메인
품질zod, problem+json 에러, pino 로깅, Vitest + testcontainers, Playwright
UITailwind + shadcn/ui
비용월 0원. R2는 카드를 등록하고 무료 한도(10GB) 안에서만 쓴다

방송 모델: 사용자 한 명이 채널 하나다. 채널 아래에 방송을 READY로 등록하고 시작·종료한다. 방송 하나는 송출 한 번이고, 종료된 방송은 다시 켤 수 없다. 다시 방송하려면 새 방송을 등록한다.

아키텍처

앱(app·worker)은 상태를 갖지 않는다. 세션, 락, 알림 전파는 모두 Redis가 맡는다. 영상 패킷은 Caddy와 앱을 거치지 않고 브라우저와 MediaMTX 사이를 직접 오간다. Caddy를 거치는 것은 연결을 맺는 HTTP 요청(WHIP/WHEP)뿐이다.

포트프로토콜용도

  • 도메인: dudung.duckdns.org 하나. Caddy가 Let's Encrypt 인증서를 자동으로 받는다. MediaMTX의 WHIP/WHEP는 같은 도메인의 /media/ 경로로 프록시해서, CORS 설정과 인증서를 따로 두지 않는다.
  • MediaMTX 이미지: bluenviron/mediamtx:1.21.3-ffmpeg(arm64 지원 확인). 훅에서 셸 명령을 쓰려고 ffmpeg 변형을 쓴다.
  • 네트워크: Caddy와 MediaMTX는 network_mode: host. app은 127.0.0.1:3000으로만 포트를 연다. Oracle은 사설 IP에 공인 IP가 1:1 NAT로 붙어 있어서, MediaMTX 설정 webrtcAdditionalHosts에 공인 IP를 적는다.
  • Oracle 방화벽: VCN 보안 목록과 서버 iptables 둘 다에서 80, 443, 8189(UDP·TCP)를 연다.
  • UDP와 TCP 8189가 모두 막히고 443만 열린 엄격한 망에서는 시청이 안 될 수 있다. README 지원 환경에 적는다. 시간이 남으면 Cloudflare TURN(월 1,000GB 무료, 443 지원)을 붙인다. 서버가 Cloudflare API로 단기 TURN 인증 정보를 발급하고, 브라우저가 RTCPeerConnection의 iceServers에 넣으면 된다.
  • CPU: 1 OCPU를 모두가 나눠 쓴다. 워커의 ffmpeg는 nice로 우선순위를 낮추고 한 번에 하나만 돌린다. 컨테이너마다 mem_limit를 둔다.
  • 비밀값: 저장소에는 .env.example만 커밋하고, 실제 값은 서버 .env와 GitHub Secrets에만 둔다.

도메인 모델과 DB 스키마

테이블은 6개다. 채널은 사용자 자체라서 테이블을 따로 두지 않는다. ID는 전부 UUIDv7, 시각은 전부 timestamptz(UTC 저장)다.

CREATE TABLE users (
  id            uuid PRIMARY KEY,
  email         text NOT NULL UNIQUE,
  password_hash text NOT NULL,              -- argon2id
  nickname      text NOT NULL UNIQUE,
  created_at    timestamptz NOT NULL DEFAULT now()
);

CREATE TYPE broadcast_status AS ENUM ('READY', 'LIVE', 'ENDED');
CREATE TYPE broadcast_source AS ENUM ('SCREEN', 'CAMERA');

CREATE TABLE broadcasts (
  id                  uuid PRIMARY KEY,
  owner_id            uuid NOT NULL REFERENCES users(id),   -- = 채널
  title               text NOT NULL,          -- 1~100자
  description         text,
  status              broadcast_status NOT NULL DEFAULT 'READY',
  source              broadcast_source,       -- 송출 시작 시 기록
  path_name           text NOT NULL UNIQUE,   -- MediaMTX 경로 'live/{id}'
  started_at          timestamptz,
  first_published_at  timestamptz,            -- 첫 송출 시각. 비어 있으면 송출 실패로 보고 READY 복귀
  ended_at            timestamptz,
  end_reason          text,                   -- OWNER | DISCONNECTED | DELETED | RECONCILED
  deleted_at          timestamptz,            -- soft delete (녹화·후원 내역 보존)
  created_at          timestamptz NOT NULL DEFAULT now(),
  updated_at          timestamptz NOT NULL DEFAULT now()
);
-- 사용자당 LIVE 방송 1개
CREATE UNIQUE INDEX one_live_per_owner ON broadcasts(owner_id) WHERE status = 'LIVE';
-- 공개 목록: READY는 노출하지 않는다
CREATE INDEX broadcasts_public ON broadcasts(status, created_at DESC)
  WHERE deleted_at IS NULL AND status <> 'READY';
CREATE INDEX broadcasts_by_owner ON broadcasts(owner_id, created_at DESC) WHERE deleted_at IS NULL;

CREATE TYPE recording_status AS ENUM ('RECORDING', 'PROCESSING', 'READY', 'FAILED');

CREATE TABLE recordings (
  id            uuid PRIMARY KEY,
  broadcast_id  uuid NOT NULL UNIQUE REFERENCES broadcasts(id),
  status        recording_status NOT NULL DEFAULT 'RECORDING',
  s3_key        text,                     -- R2: recordings/{broadcastId}.mp4
  size_bytes    bigint,                   -- 용량 정책 계산용
  duration_sec  integer,                  -- 최대 3600
  error         text,
  created_at    timestamptz NOT NULL DEFAULT now(),
  updated_at    timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE comments (
  id            uuid PRIMARY KEY,
  broadcast_id  uuid NOT NULL REFERENCES broadcasts(id),
  author_id     uuid NOT NULL REFERENCES users(id),
  body          text NOT NULL,            -- 1~300자
  deleted_at    timestamptz,
  created_at    timestamptz NOT NULL DEFAULT now(),
  updated_at    timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX comments_by_broadcast ON comments(broadcast_id, id DESC);

CREATE TYPE donation_status AS ENUM ('PENDING', 'DONE', 'FAILED');

CREATE TABLE donations (
  id            uuid PRIMARY KEY,
  order_id      text NOT NULL UNIQUE,     -- 서버가 발급, 토스에 전달
  broadcast_id  uuid NOT NULL REFERENCES broadcasts(id),
  donor_id      uuid NOT NULL REFERENCES users(id),
  recipient_id  uuid NOT NULL REFERENCES users(id),  -- 방송 owner, 서버가 채움
  amount        integer NOT NULL CHECK (amount BETWEEN 1000 AND 100000),
  message       text,
  status        donation_status NOT NULL DEFAULT 'PENDING',
  payment_key   text UNIQUE,              -- 승인 후 기록, 중복 적립 방지
  approved_at   timestamptz,
  created_at    timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX donations_by_broadcast ON donations(broadcast_id) WHERE status = 'DONE';

CREATE TABLE webhook_events (
  source       text NOT NULL,             -- toss
  event_id     text NOT NULL,
  received_at  timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (source, event_id)
);
  • 방송 삭제는 soft delete다. 녹화와 후원 내역이 방송을 참조하므로 행을 지우지 않는다. 삭제된 방송의 녹화는 목록과 상세에서 숨긴다.
  • 녹화는 방송당 1개다. 송출자가 재접속해도 같은 MediaMTX 경로에 조각이 이어서 쌓이고, 종료 후 하나로 합친다.
  • 웹훅 중복 제거(토스): webhook_events insert를 상태 변경과 같은 트랜잭션에서 한다. 처리가 실패하면 함께 롤백돼서, 재전송된 이벤트가 중복으로 버려지지 않는다. Redis SET NX는 동시 처리를 막는 30초 락으로만 쓴다.
  • MediaMTX 훅은 내부 호출이고, 모든 상태 전환이 조건부 업데이트라 같은 훅이 두 번 와도 결과가 같다. 그래서 별도 중복 제거 기록을 두지 않는다.
  • 후원 합계는 SUM(amount) WHERE status='DONE' 쿼리로 계산한다. 별도 합계 컬럼을 두지 않아 정합성 문제가 없다.
  • 후원은 LIVE 방송에만 가능하다. 30분 넘게 결제되지 않은 PENDING 주문은 정리 작업이 FAILED로 바꾼다.

방송 상태와 동기화

DB가 상태의 기준이다. MediaMTX는 송출·시청 요청마다 앱에 허용 여부를 묻고, 앱은 DB가 LIVE일 때만 허용한다. LIVE 중 삭제는 ENDED(DELETED)를 거쳐 soft delete된다.

  • 모든 전환은 조건부 업데이트다. UPDATE broadcasts SET status='ENDED' ... WHERE id=? AND status='LIVE'. 영향 행이 0이면 이미 다른 경로로 전환된 것이므로 아무 일도 하지 않는다. 종료 버튼과 훅이 동시에 와도 한 번만 처리된다.
  • 사용자당 LIVE 1개는 부분 UNIQUE 인덱스가 보장한다. 두 번째 start는 409.
  • 송출 감지: 송출이 붙으면 MediaMTX runOnReady 훅이 /internal/media/ready를 부른다. 앱은 first_published_at을 처음일 때만 기록하고, 녹화 행을 RECORDING으로 만들고, 대기 중인 종료 작업을 취소한다.
  • 끊김 감지: 송출이 끊기면 runOnNotReady 훅이 /internal/media/not-ready를 부른다. 앱은 end-if-absent 지연 작업(30초)을 등록한다. 작업이 실행될 때 Control API로 확인해서 송출자가 없으면 ENDED(DISCONNECTED)로 바꾼다.
  • 송출 없이 끝남: start 때 start-timeout 지연 작업(2분)을 등록한다. 2분이 지나도 first_published_at이 비어 있으면 UPDATE ... SET status='READY', started_at=NULL, source=NULL WHERE id=? AND status='LIVE' AND first_published_at IS NULL로 되돌린다. 같은 방송으로 다시 시작할 수 있다. "한 방향" 원칙의 유일한 예외다.
  • 종료 순서: DB를 ENDED로 바꾼 뒤 Control API로 송출 세션을 끊는다(kick). 끊기 전에 재연결을 시도해도 인증 훅이 거절하므로, 끊기가 실패해도 정합성 정리가 1분 안에 다시 끊는다.
  • 정합성 정리(reconcile): 1분마다 워커가 pg_advisory_lock을 잡고 DB의 LIVE 목록과 Control API의 송출 중인 경로를 비교한다. DB는 LIVE인데 송출자가 없고 시작한 지 2분이 지났으면, 위 규칙대로 ENDED(RECONCILED) 또는 READY 복귀. MediaMTX에서는 송출 중인데 DB가 LIVE가 아니면 끊는다.
  • 녹화와 상태는 별개다. 방송이 ENDED가 되면 워커가 녹화를 합치고 올린 뒤 녹화가 READY가 된다.
  • 내부 훅 보호: /internal/*는 Caddy가 외부 요청에 404를 돌려주고, 앱도 X-Internal-Secret 헤더를 확인한다.

인증과 인가

권한 검증은 전부 서버의 서비스 계층에서 한다. middleware는 쿠키 파싱과 리다이렉트만 하고, 권한 판단은 하지 않는다.

토큰

토큰저장수명내용
AccesshttpOnly 쿠키 at, Path=/10분sub, jti, exp, ES256 서명
RefreshhttpOnly 쿠키 rt, Path=/api/auth14일sub, jti, family. Redis에 auth:rt:{jti} 저장
송출 토큰응답 바디, 클라이언트 메모리15분무작위 문자열. Redis media:pub:{token} → {broadcastId, userId}. WHIP 요청 URL의 ?token=으로 보낸다
시청없음-인증 훅이 방송 LIVE 여부만 확인
  • 쿠키 공통: HttpOnly; Secure; SameSite=Lax.
  • Refresh rotation: 사용하면 새로 발급하고, 기존 jti는 30초 동안 "교체됨(새 토큰 참조)"으로 남긴다. 30초 안에 같은 jti가 다시 오면 같은 새 토큰을 돌려준다(탭 2개가 동시에 refresh하는 경우). 30초가 지난 뒤 다시 오면 탈취로 보고 auth:family:{family} 전체를 폐기한다.
  • 클라이언트 refresh: refresh 쿠키가 Path=/api/auth라서 middleware는 페이지 이동 중에 재발급할 수 없다. 클라이언트 AuthProvider가 /api/me 401을 받으면 /api/auth/refresh → router.refresh() 순으로 처리하고, 탭 간 중복 요청은 navigator.locks로 하나로 묶는다.
  • 로그아웃: refresh jti 삭제, access jti를 auth:bl:{jti}(TTL = 남은 수명)에 등록, 쿠키 삭제.
  • 서명키: ES256 키쌍을 환경변수로 주입한다.
  • CSRF: 쓰기 요청(POST·PATCH·DELETE)은 Origin 헤더가 앱 도메인과 같을 때만 통과한다. 외부 서버가 호출하는 /api/webhooks/*는 제외하고 조회 API로 검증한다.
  • 미디어 인증: MediaMTX authMethod: http. 송출(publish)은 토큰이 유효하고, 토큰의 사용자가 방송 소유자이고, 방송이 LIVE일 때만 허용한다. 시청(read)은 방송이 LIVE일 때만 허용한다. 나머지 동작은 거절한다.
  • 테스트 계정: 고정 계정 streamer1~3@dudung.test, viewer1~2@dudung.test. 비밀번호는 README에 적고, 로그인 화면에 계정별 원클릭 버튼을 둔다. 로그인할 수 없는 demo 계정 소유의 종료된 방송과 녹화를 seed해서, 심사자가 지울 수 없는 "다른 사용자 방송"과 다시보기 예시로 쓴다.

핵심 흐름

송출 시작

  1. 소유자가 방송 등록 → READY.
  2. 스튜디오에서 미디어 권한부터 확보한다(getDisplayMedia 또는 getUserMedia). 권한 거부 시 서버 호출 없이 중단.
  3. POST /start { source } → 서버가 소유자·READY 확인 → UPDATE ... SET status='LIVE' WHERE id=? AND status='READY'(영향 행 0이면 409) → 송출 토큰 발급 → start-timeout(2분) 등록 → { whipUrl, token } 응답.
  4. 클라이언트가 RTCPeerConnection에 영상 트랙 1개와 믹스된 음성 트랙 1개를 넣고, setCodecPreferences로 H.264를 우선한다.
  5. WHIP: offer SDP를 POST /media/live/{id}/whip?token=…로 보내고 answer를 적용한다.
  6. MediaMTX가 /internal/media/auth에 action=publish로 묻는다. 앱은 토큰·소유자·LIVE를 확인해 허용한다.
  7. 송출이 붙으면 runOnReady 훅 → first_published_at 기록, 녹화 RECORDING. MediaMTX는 경로 설정에 따라 디스크에 녹화를 시작한다.

시청

  1. 상세 화면 진입 → LIVE면 WHEP: POST /media/live/{id}/whep(토큰 없음). 인증 훅은 action=read에 대해 LIVE만 확인한다. READY면 대기 화면에서 5초마다 상태를 확인한다.
  2. <video muted autoplay playsinline>로 재생한다. 영상과 음성이 한 연결로 오므로 "탭해서 소리 켜기" 버튼은 video의 음소거만 풀면 된다.
  3. SSE를 구독해서 댓글·후원·제목 변경·시청자 수를 반영한다. broadcast.ended를 받으면 "방송이 종료되었습니다" 화면으로 바꾼다.
  4. WebRTC 연결이 끊기면(connectionState=failed) 3초 뒤 상태를 확인하고, 아직 LIVE면 WHEP로 다시 연결한다.

종료

  1. 정상 종료: POST /end → 서버가 소유자·LIVE 확인 → ENDED(end_reason=OWNER) → Control API로 송출 세션 끊기 → SSE broadcast.ended.
  2. 비정상 종료: 송출자 탭 닫힘·네트워크 끊김 → runOnNotReady 훅 → 30초 유예 후에도 송출자가 없으면 ENDED(DISCONNECTED). 유예는 BullMQ 지연 작업으로 처리한다.
  3. 화면공유 "공유 중지" 클릭(track.onended) → 클라이언트가 POST /end 호출.
  4. 송출자 클라이언트는 종료 응답을 받거나 연결이 끊기면 로컬 트랙을 모두 stop()하고, AudioContext와 PeerConnection을 닫는다. 서버가 세션을 끊어도 브라우저의 카메라·화면 캡처는 따로 꺼야 한다.

녹화

  1. MediaMTX가 /recordings/live/{id}/ 아래에 fMP4 조각을 10분 단위로 저장한다. 송출자가 재접속해도 같은 경로에 이어서 쌓인다.
  2. 방송이 ENDED가 되면 워커의 process-recording 작업이 녹화를 PROCESSING으로 바꾸고 조각을 하나로 합친다: ffmpeg -f concat -i list.txt -c:v copy -c:a aac -t 3600 -movflags +faststart out.mp4. 영상은 재인코딩하지 않고, 음성만 Opus → AAC로 바꿔 모든 브라우저에서 재생되게 한다. 60분이 넘는 부분은 잘라낸다.
  3. R2에 업로드(@aws-sdk/lib-storage, 고정 파트 크기)한 뒤 s3_key, size_bytes, duration_sec를 기록하고 READY. 서버에 남은 조각은 바로 지운다. 실패하면 3회 재시도 후 FAILED.
  4. 용량 정책: 업로드 후 READY 녹화의 size_bytes 합이 8GB(R2 무료 10GB의 80%)를 넘으면, demo 계정 것을 제외하고 가장 오래된 녹화부터 R2 객체와 행을 지워 8GB 아래로 맞춘다. 이 동작은 README에 적는다.
  5. 재생: GET /api/recordings/:id가 presigned URL(1시간)을 주고, <video src>로 재생한다.

후원

  1. POST /donations { amount, message } → 서버가 방송이 LIVE인지 확인하고 recipient_id = 방송 owner로 고정, orderId 발급, PENDING 저장. 후원 창에는 "받는 사람: {닉네임}"을 크게 보여준다.
  2. 클라이언트가 토스 결제위젯을 위젯 연동 키(test_gck_)와 orderId·금액으로 호출한다(테스트 모드).
  3. 성공 리다이렉트 → POST /donations/confirm → 서버가 orderId의 저장 금액과 요청 금액을 대조 → 토스 승인 API 호출(Idempotency-Key = orderId).
  4. 승인 응답의 orderId·totalAmount·status=DONE 재확인 → UPDATE ... SET status='DONE', payment_key=? WHERE order_id=? AND status='PENDING'.
  5. 영향 행이 1이면 SSE donation.created로 방송 화면에 후원 알림을 띄운다. 0이면 이미 처리된 것으로 보고 기존 결과를 돌려준다.
  6. 승인 API가 ALREADY_PROCESSED_PAYMENT를 돌려주면(새로고침 등으로 confirm 재요청) 결제 조회 API로 상태를 확인해 4번과 같은 조건부 업데이트를 한다.
  7. 토스 웹훅은 바디를 믿지 않고 paymentKey로 결제 조회 API를 다시 불러 확인한 뒤, 같은 조건부 업데이트를 거친다. 반복 통지가 와도 한 번만 적립된다.
  8. 승인은 됐는데 DB 반영 전에 서버가 죽은 경우: 정리 작업이 10분 넘은 PENDING 주문을 orderId로 조회해 DONE이면 반영하고, 30분 넘게 결제가 없으면 FAILED로 바꾼다.

실시간 알림 (SSE)

  1. 시청 화면은 GET /api/broadcasts/:id/events(text/event-stream)를 연다. 앱은 Redis 채널 bc:{id}를 구독해서 받은 이벤트를 흘려보낸다.
  2. 쓰기 API(댓글, 후원 확정, 방송 수정, 종료)는 DB 반영 후 Redis에 publish한다. 앱이 여러 개 떠 있어도 모든 SSE 연결로 전달되므로 stateless가 유지된다.
  3. 이벤트: comment.created, comment.updated, comment.deleted, donation.created, broadcast.updated, broadcast.ended, viewers(10초마다 시청자 수).
  4. 15초마다 하트비트 주석(:)을 보내 프록시 타임아웃을 막는다. Caddy는 text/event-stream 응답을 버퍼링 없이 바로 흘려보낸다. 끊기면 EventSource가 자동으로 다시 연결하고, 클라이언트는 재연결 때 목록 API로 빠진 댓글을 보정한다.

클라이언트 미디어 처리

영상은 H.264로 송출하고, 오디오는 마이크와 화면 소리를 WebAudio로 섞어 트랙 1개로 publish한다. 연결은 WHIP(송출)와 WHEP(시청) 표준을 쓴다. 각각 SDP offer/answer를 HTTP로 한 번 주고받는 100줄 안팎의 코드이고, MediaMTX 저장소의 예제(MIT)를 참고해 출처를 README에 적는다.

// 시작 버튼 클릭 핸들러 안에서 실행 (AudioContext는 사용자 동작이 필요)
const ctx = new AudioContext();
const dest = ctx.createMediaStreamDestination();
ctx.createMediaStreamSource(micStream).connect(dest);
if (screenStream.getAudioTracks().length > 0) {
  ctx.createMediaStreamSource(screenStream).connect(dest);   // 탭·시스템 소리
}
const mixed = dest.stream.getAudioTracks()[0];               // 이 트랙 하나만 송출

예외 처리

  • 화면공유 "공유 중지" → track.onended → POST /end.

  • 모바일 백그라운드 전환 → visibilitychange로 감지. 30초 안에 돌아오면 장치를 다시 획득해 RTCRtpSender.replaceTrack()으로 갈아 끼운다. 연결을 다시 맺지 않으므로 송출과 녹화가 이어진다. 30초가 지나면 서버 측 유예 처리로 ENDED.

  • 방송 종료 → 로컬 트랙 전부 stop(), AudioContext close(), PeerConnection close().

키 이름과 훅의 환경변수 치환 방식은 구현할 때 MediaMTX 문서로 다시 확인한다.

CI/CD

  1. PR: lint, typecheck, 통합 테스트(testcontainers).
  2. main 머지: GitHub Actions ARM64 러너(ubuntu-24.04-arm, 공개 저장소 무료)에서 이미지 빌드 → GHCR push → SSH로 서버에서 docker compose pull && docker compose up -d.
  3. 마이그레이션은 앱 시작 전 one-shot migrate 컨테이너가 한 번 실행한다(depends_on).

로컬 실행

  • docker compose -f deploy/compose/compose.local.yml up 하나로 app, worker, PostgreSQL, Redis, MediaMTX, MinIO(R2 대체)를 띄운다. 도메인과 클라우드 계정 없이 동작한다.
  • PC 브라우저는 http://localhost가 보안 컨텍스트라 화면공유·카메라가 동작한다. 휴대폰 송출은 HTTPS가 필요해서 배포 서버로 확인하도록 README에 적는다.
  • 토스 테스트 키가 없으면 후원 UI를 숨기고, 나머지 기능은 그대로 동작한다.

서버와 가용성

  • 서버: Oracle Cloud Always Free ARM(A1) 1 OCPU / 8GB, 오사카 리전. 메모리 상한 예시: PostgreSQL 1GB, app 1GB, worker 512MB, Redis 256MB, MediaMTX 256MB, Caddy 128MB.
  • Oracle은 CPU·네트워크·메모리 사용률이 모두 낮은 Always Free 인스턴스를 유휴로 보고 정지시킬 수 있다. 외부 업타임 모니터(무료 서비스)가 /readyz를 1분마다 확인하고, 실패하면 알림을 받아 다시 켠다.
  • PostgreSQL은 named volume에 두고, 하루 한 번 db-backup 작업이 pg_dump를 R2 backups/에 올린다(7일 보관).

로깅과 헬스체크

  • pino JSON 로그, 요청마다 requestId 헤더 전파. 미디어 인증 거절, 훅, 결제, 상태 전환은 반드시 로그를 남긴다. 송출 토큰은 로그에 남기지 않는다.
  • /healthz는 프로세스 생존만, /readyz는 DB·Redis·MediaMTX API까지 확인한다.

평가에서 가장 비중이 큰 권한 검증과 상태 전환을 자동 테스트로 증명하고, 그 결과를 README에 링크한다.

층도구대상

통합Vitest + testcontainers (Postgres, Redis)권한 매트릭스 전체, 미디어 인증 훅(토큰·소유자·상태별 허용과 거절), 조건부 업데이트 동시성, 훅 순서 뒤바뀜, 토스 웹훅 중복·처리 실패 후 재전송, 후원 중복 승인·ALREADY_PROCESSED_PAYMENT, refresh 동시 요청
E2EPlaywright (--use-fake-device-for-media-stream, --use-fake-ui-for-media-stream) + 로컬 MediaMTX송출 → 다른 브라우저 컨텍스트 시청 → 종료, 시청 화면 종료 전환, 종료 후 같은 토큰으로 재송출 거절, 녹화 READY 후 재생
수동실기기iOS Safari·Android Chrome 카메라 송출, Windows 시스템 소리, 모바일 데이터망, UDP가 막힌 망(TCP 폴백), 화면공유 중 창 크기 변경 후 녹화 재생
  • MediaMTX Control API와 토스 API는 통합 테스트에서 인터페이스 뒤로 감추고 가짜 구현을 주입한다.
  • 동시성 테스트: 같은 방송에 start 2건 동시 → 1건만 성공, 같은 orderId confirm 2건 동시 → 적립 1건, 같은 refresh 토큰 2건 동시 → 둘 다 성공하고 로그아웃되지 않음.
  • 구현 첫날 확인할 위험: 화면공유 중에 공유 창 크기를 바꿨을 때 MediaMTX 녹화 조각과 합친 MP4가 정상 재생되는지. 문제가 있으면 송출 해상도를 고정하는 방법을 찾는다.
  • scripts/authz-check.sh를 배포 서버에 돌린 결과를 README에 붙인다.

시연 영상 시나리오

장면내용
1. PC 송출로그인 → 방송 등록 → 화면공유(탭 소리 체크) + 마이크 → 음량 미터 확인 → 휴대폰에서 시청(소리 포함) → 종료 → 휴대폰 화면이 종료 안내로 바뀜
2. 모바일 송출휴대폰 로그인 → 카메라 송출 → PC에서 시청 → 휴대폰에서 종료 → PC 화면 전환
3. 권한비로그인 시청 가능, 비로그인으로 방송 등록 → 로그인 화면 이동, 다른 사용자의 수정·삭제 → 403 (authz-check.sh 실행 화면)
4. 선택 기능댓글 작성·수정·삭제, 테스트 결제 후원과 합계, 다시보기 재생

송출 기기와 시청 기기가 한 화면에 같이 보이게 찍는다(화면 녹화 + 휴대폰 미러링 또는 카메라 촬영).
